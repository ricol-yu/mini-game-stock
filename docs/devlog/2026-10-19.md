## 备注

今天确认了两件事对项目的长期价值：

1. **「不要先导代码」这条规矩的本质是「先验证技术选型，再迁移业务逻辑」**。
   WXS 手感是迁移路径上的最大未知数（touchmove 在 WXS 里能不能不丢帧、能不能
   跟手，模拟器回答不了）。如果一上手就把 prototype 拷进 `pages/`，就会面临
   「是 prototype 的问题还是 WXS 的问题」这种二义性诊断。先用 spike 隔离验证，
   至少能分清是引擎层还是业务层。
2. **「同一份文件不要两边同时改」比「哪台机器是主源」更有约束力**。
   这次 Mac 端唯一做的就是 `HANDOFF.md` 一份文件，Windows 端 pull 不会看到任何
   prototype 相关 diff。零冲突面。哪天 prototype 进仓库了也按这个原则做：
   谁在改就先 push，接到通知的人不要碰那个文件。

## 追加：合并 v3 原型（含一个真实冲突）

用户去申请微信测试号，我这边同步把 Mac 上的 v3 原型合并进仓库。合并前做了三项检查，
**其中一项是真冲突，值得单独记**：

1. **路径重叠** —— `prototype.html` / `design.html` 仓库中不存在，纯新增，零冲突
2. **`data/cards.json` 与 prototype.html 的一致性** —— ⚠️ **真冲突**
   - 仓库里的 `cards.json` 是 10-16 生活成本定标（×1.3）**之前**的版本
   - 当前 `prototype.html` 是定标**之后**的版本
   - 差异：20 处 `spend` 数值 + 8 处卡面文案 label
   - 方向统一：4200 → 5500、3000 → 3900、900 → 1200 等
   - 处理：以 `prototype.html` 为真源（`AGENTS.md` 明说「从原型自动抽取」），
     重跑 `tools/extract-cards.js` 覆盖 `data/cards.json`
3. **`design.html` 结论与 `AGENTS.md` 是否打架** —— 无冲突
   - 技术选型：design.html 明确推荐小程序，与 AGENTS.md 一致
   - 变现方式：design.html 只在合规风险章节提到内购，作为「要版号」的对照，
     结论是「按无版号可变现推进，版号做 Plan B」，与 AGENTS.md 的纯广告一致

**为什么第 2 项值得记**：`cards.json` 是 prototype 的**派生物**，不是独立资产。
只要 prototype 改了数值而没重抽，这个文件就静默过期——它不会报错、不会冲突、
git 也看不出来，但所有基于它的分析（比如那 18 张支配选项的判定）都会建立在
错误数值上。这类「派生文件」的同步，最好在每次改 prototype 后当成固定动作，
或者干脆在 `extract-cards.js` 里加个校验（比对源文件的 hash）。

顺带确认：重抽后支配选项仍是 **18 张**（与 Windows 那晚的数字一致）。
数值缩放不改变两个选项的相对优劣，所以支配关系没变——这也侧面说明
那 18 张的问题是**结构性的**（选项设计本身缺权衡），不是数值没调好。
