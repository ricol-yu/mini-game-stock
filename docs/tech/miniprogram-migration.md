# 从网页原型迁移到微信小程序

> 本文替换了早先的「迁移到小游戏」版本。那个版本的前提是错的——
> 项目已确定走**小程序**，不是小游戏。保留这段说明，是为了记住这个判断为什么改。

## 一、结论：选小程序是对的

理由不是「小游戏技术栈比较坑」，而是更本质的一条：

**这个游戏是 UI 型，不是渲染型。**

原型 655 行里，真正属于「游戏」的部分——数值公式、状态机、结算逻辑——大概
200 行。剩下 400 多行全是界面：卡牌的圆角阴影、四根渐变进度条、文字排版、
印章的旋转角度、三张卡的层层缩放。

用 WXSS 做这些，几乎照抄。
用 Canvas 做这些，全部手写。

## 二、复用率对照

| 原型里的东西 | 小程序 | 小游戏 |
|---|---|---|
| 卡牌布局 / 圆角 / 阴影 | CSS 直接抄 | `fillRect` + 手算坐标 |
| 四根进度条（含渐变、条纹） | 直接抄 | `createLinearGradient` + 手工填充 |
| **文字自动换行** | 浏览器负责 | 自己 `measureText` 逐字断行 + 避头尾 |
| **emoji 头像** | 正常显示 | 各机型差异，低端安卓可能出现空白方块 |
| 卡牌拖动旋转 | `transform` + `transition` | 每帧重绘整张卡 |
| 三张卡层叠（scale + translateY） | 直接抄 | 手算缩放与位移 |
| 触屏坐标 | 原生 | 要除以 scale，还要处理 DPR |
| 数值结算公式 | 原样搬 | 原样搬 |
| 63 张卡数据 | 原样搬 | 原样搬 |

前七项在小游戏方案里是**主要工作量**，切换到小程序后**全部消失**。
这是选小程序最大的实际收益，比「分享方便」重要得多。

## 三、但坑换了一个：手势不能用 setData

小程序做 Tinder 式滑卡，唯一的硬骨头在这里。

在 `bindtouchmove` 里每帧调 `setData` 更新卡牌位置，数据要从逻辑层
传到渲染层，60fps 根本撑不住——手感会明显「粘手」，越快越明显。

**正解：WXS 响应事件。**

WXS 运行在渲染层，可以直接改样式，不走 `setData`，零通信开销：

```js
// game.wxs
function touchmove(e, ins) {
  var el = ins.selectComponent('.card-top')
  el.setStyle({ transform: 'translate(' + dx + 'px, 0) rotate(' + dx * 0.045 + 'deg)' })
}
```

代价：WXS 是受限的 JS 子集，不能调 `wx.*` API，不能 `new`，访问不到页面 `data`。
手势逻辑得用这种受限语法重写。

**替代方案 `movable-area` + `movable-view` 不推荐**——层叠卡片、印章透明度、
松手飞出这几件事联动起来很别扭，手感不如手写。

**这条必须在写业务代码之前验证。** 半小时能验完；方向错了要推倒重来。

## 四、WXSS 兼容性：两个具体问题

逐条扫了原型那 101 行 CSS，绝大部分能直接搬，两处要改：

### 1. 通配符选择器

```css
*{box-sizing:border-box;-webkit-tap-highlight-color:transparent}
```

WXSS **不支持 `*` 通配符**。改成显式列举：

```css
page, view, text, image, button { box-sizing: border-box; }
```

### 2. `inset` 简写

```css
.card{position:absolute;inset:4px 0 8px}
```

部分基础库不认 `inset` 简写，拆开写：

```css
.card{position:absolute;top:4px;right:0;bottom:8px;left:0}
```

### 其余能直接用的

- CSS 变量（`:root` 改成 `page`）
- `linear-gradient` / `repeating-linear-gradient`
- `box-shadow`、`border-radius`、`@keyframes`、`transition` + `cubic-bezier`
- `@media`、`vh`、`flex`

### 要删掉的

- `html,body{}` —— 小程序没有这两个标签，用 `page`
- `cursor:grab` —— 触屏设备无意义

## 五、原型的 `render()` 要改成数据驱动

原型里直接操作 DOM：

```js
$("b-mind").style.width = S.mind + "%";
$("r-money").classList.toggle("warn", n < INIT * 0.35);
```

小程序里没有 `document`，两条路：

| 更新频率 | 做法 |
|---|---|
| 低频（一天一次：进度条、数字、状态标签） | `this.setData()`，代价可忽略 |
| 高频（拖动时的卡牌位置） | WXS `setStyle`，绝不走 setData |

判断标准很简单：**每帧都要变的用 WXS，一天变几次的用 setData。**

## 六、建议的目录结构

```
mini-game-stock/
├── miniprogram/
│   ├── pages/game/
│   │   ├── game.js          状态 + 结算（逻辑层）
│   │   ├── game.wxml        卡牌、进度条、结局页
│   │   ├── game.wxss        从原型 CSS 改造
│   │   └── game.wxs         手势（渲染层，零 setData）
│   ├── data/cards.json      63 张卡
│   └── app.json / app.wxss
├── core/                    纯逻辑，两端共用（web 调试版也读它）
├── prototype.html           保留，见第九节
└── docs/
```

`core/` 里不出现任何平台 API——既没有 `document`，也没有 `wx`。
这样网页调试版和小程序版读同一份逻辑，不会出现「两边手感不一样」这种无解 bug。

## 七、⚠️ 类目不可逆：这比技术选型更要紧

查了平台规则，有一条必须提前知道：

**小程序注册时选「游戏」类目是单向不可逆操作。**

- 选了「游戏」= 就是小游戏，改不回来，后台还会隐藏一批能力
  （附近的小程序、模板消息、客服消息、业务域名配置等）
- 反过来，已经选了其他类目，也不能再回头加游戏类目
- 选错只能重新注册新账号，**AppID、已有用户、数据全部归零**

所以：**如果账号还没注册，先别急着点「游戏」两个字。**

内容层面的风险：这个游戏是卡牌决策 + 数值模拟，本质更接近「互动小说 / 人格测试」。
按娱乐互动类定位，通常比「游戏」类目好过审。但如果审核判定为游戏内容，
会被要求改类目——那时只能重新注册。**这是这个项目最大的不确定性，不是技术问题。**

## 八、变现：个人主体两条路都堵着

先说清楚，免得做到一半才发现：

| | 小程序 | 小游戏 |
|---|---|---|
| 支付接口 | 微信支付、云闪付 | 仅小游戏虚拟支付（米大师） |
| 个人主体能否内购 | **不能**（需企业/个体工商户） | **不能**（平台禁止开通虚拟支付） |
| 能做的变现 | 流量主广告（需累计独立访客） | 激励视频 / Banner 广告 |

如果打算靠内购赚钱，选哪个都得先解决主体资质。如果只是作品或引流，
这条不构成选型依据。

## 九、保留网页版，价值比小游戏方案下更高

`prototype.html` 别删。原因：

- WXSS 和 CSS 几乎一样，**网页版就是免费的小程序预览**，改样式不用等编译
- 调数值时改一行刷新就见效，小程序每次都要编译 + 真机调试
- 发给别人试玩，一个链接就行

前提同样是逻辑共用 `core/`。

## 十、迁移顺序

1. **WXS 滑卡验证**（1 小时，最高优先级）—— 一张卡跟手、松手飞出，真机看手感
2. 静态页面还原：卡牌布局、进度条、行情区
3. 接逻辑：`core/` 的结算函数接进出卡回调
4. 结局页 + 分享
5. 真机调：iPhone SE、一台中低端安卓

第 1 步不通，后面的努力都有风险。所以它排在最前面。
