# 从网页原型迁移到微信小游戏

> 基于 `prototype.html` v3 的实际代码结构，逐条列出迁移时必须重写的部分。
> 写这份文档的目的：在动手之前把返工点找出来。

## 结论先说

**能直接复用的：数据、数值公式、文案。大约占这个游戏 70% 的价值。**
**必须重写的：全部渲染和交互。** 网页原型用的是 DOM + CSS，
微信小游戏里没有 DOM，没有 div，没有 CSS，只有一块 Canvas。

这不是「移植」，是「换一层皮」。核心资产（63 张卡、七种状态、十四个结局、
那套数值公式）可以整块搬过去，但表现层要重新写。

**不要引入游戏引擎。** 卡牌 + 进度条 + 文字，原生 Canvas 足够，
引 Cocos / Laya 只会让包体和调试成本翻倍。

## 一、没有 DOM 意味着什么

原型里这些都要重写：

| 原型写法 | 小游戏里怎么办 |
|---|---|
| `div` + CSS 布局 | 全部用 `ctx.fillRect` / `fillText` 手绘坐标 |
| `border-radius` 圆角卡片 | `ctx.roundRect()`（基础库 2.11.0+，低版本需手写路径） |
| `linear-gradient` 进度条 | `ctx.createLinearGradient()` |
| `box-shadow` | `ctx.shadowBlur`（性能差，建议改用两层矩形模拟） |
| CSS `transition` + `cubic-bezier` | 自己在 `requestAnimationFrame` 里做缓动插值 |
| `card.style.transform` 拖动 | 记录偏移量，每帧重绘整张卡 |
| `pointerdown/move/up` | `wx.onTouchStart/Move/End` |
| `setTimeout` 动画 | 可以用，但和帧循环混用容易乱，建议统一进帧循环 |
| `innerHTML` 拼卡面 | 拆成绘制函数，按字段画文本 |

## 二、五个具体的坑

### 1. 文字不会自动换行

Canvas 的 `fillText` 只画一行，超长直接溢出。卡面正文是整段中文，
必须自己按宽度断行：

```
逐字累加 → measureText 量宽 → 超过上限就换行 → 记录每行 y
```

中文没有空格，只能按字符断。注意：标点符号不能出现在行首（避头尾规则），
否则看起来会很业余。真要做干净，需要一份简单的避头尾字符表。

**这条是整个迁移里最费时间的一块，别低估。**

### 2. emoji 在不同机型上长得不一样

卡池里每张卡都有 emoji 头像（💍 👧 😰 🫧 …），状态条也用 emoji。
Canvas 画 emoji 依赖系统字体，iOS 和 Android 差异明显，部分老旧 Android
甚至画成空白方块。

三个选项：

- 接受差异（最省事，但安卓低端机可能很难看）
- 换成图片资源（每个 emoji 一张 png，包体 +200KB 左右，但一致性最好）
- 换成矢量图标（自己画，工作量最大，最可控）

建议：**先接受差异跑通，上线前如果 iOS/Android 观感差太多再换图片**。
别在验证玩法阶段纠结这个。

### 3. 触摸坐标要换算

设计稿是 344×700 的逻辑尺寸，实际屏幕千奇百怪。需要：

```
scale = 屏宽 / 344
绘制前 ctx.scale(scale, scale)
触摸时 逻辑坐标 = 触摸坐标 / scale
```

漏掉换算的表现是：**手指位置和卡片位置对不上**，而且在小屏上偏得更多。
这是最常见的 Canvas 适配 bug。

另外 `devicePixelRatio` 也要处理，否则高分屏上线条发虚。

### 4. 帧循环与状态更新要分开

原型里 `fly()` 里直接 `resolve()` → `tick()` → `render()`，同步执行。
Canvas 里如果照搬，会出现「滑走动画还没播完，数据已经变了」的错位。

正确结构：

```
状态机：idle → dragging → flying → resolving → idle
每帧：读状态 → 算插值 → 重绘
动画结束的回调里才改数据
```

### 5. 全量重绘的性能

原型里改一个进度条只动一个 DOM 节点。Canvas 没有增量更新，
每帧都要把整屏画一遍——四个进度条 + 状态标签 + 三张层叠卡 + 卡面文字。

60fps 下每秒 60 次全量绘制，中低端安卓会吃力。两个对策：

- **分层**：静态层（顶部 HUD、导航）和动态层（卡牌）用两块 Canvas 叠放，
  静态层只在数据变化时重绘一次
- **缓存**：卡面文字排版结果缓存起来，拖动时只改偏移量，不重新断行

第二条尤其重要：断行是逐字 `measureText`，每帧重算会直接卡死。

## 三、数据层的改造

### `when: function` 不能留

原型里卡牌触发条件写成了函数：

```js
when: function(){ return !S.st.baby; }
```

这在网页里没问题，但在小游戏里有两个麻烦：不能序列化成 JSON（不能进远程配置、
不能热更），也不方便做可视化编辑。

**改成声明式条件**，例如：

```json
"when": [{ "field": "status", "key": "baby", "op": "absent" }]
```

然后写一个小的条件求值器（20 行左右）。好处是卡池可以完全数据驱动，
未来做「卡牌编辑器」或者按版本调整数值都不用改代码。

### 数值和文案抽成独立文件

现在 63 张卡硬编码在 `prototype.html` 的 JS 里，改一张卡要动主文件。
已经用 `tools/extract-cards.js` 抽成 `data/cards.json` 了，
迁移时直接读这份数据，逻辑层不碰文案。

**收益**：调数值、改文案不需要理解引擎代码，两台设备上谁都能改，
冲突面也从「一个大 HTML 文件」缩小到「一行 JSON」。

## 四、建议的目录结构

```
mini-game-stock/
├── core/                  纯逻辑，不依赖任何渲染
│   ├── state.js           状态对象与初始化
│   ├── engine.js          tick / apply / resolve / check
│   └── conditions.js      声明式条件求值
├── data/
│   ├── cards.json         63 张卡（已生成）
│   └── endings.json       14 个结局
├── platform/
│   ├── web/               网页版（保留，用于快速调试）
│   └── wx/                小游戏版（正式交付）
├── tools/
│   └── extract-cards.js   从原型抽卡池（已有）
└── docs/
```

`core/` 里一行渲染代码都不许有——这是这条分层唯一的规矩。
只要守住这条，未来换引擎、加平台都不用重写逻辑。

## 五、顺序建议

1. **先跑通静态卡面**：一张卡画在 Canvas 上，文字能正确断行、居中对齐
2. **再加滑动**：touch 拖动 + 旋转 + 印章透明度 + 松手回弹或飞出
3. **再接逻辑**：`core/` 里的结算函数接进飞出回调
4. **最后补 HUD**：四条进度条、状态标签、行情区、结局页
5. **真机调**：iPhone SE（小屏）、一台中低端安卓（性能）

第 1 步和第 2 步会花掉总时间的一半以上。这不是因为难，是因为 Canvas
的坐标要一个个调，没有 CSS 那种「差不多就行」的余地。

## 六、一个建议：保留网页版

别急着删 `prototype.html`。它有两个用途：

- **调数值**：改一行刷新就见效，小游戏每次都要编译 + 真机调试
- **给不懂代码的人看**：发个链接就能玩，比发体验版二维码方便

前提是逻辑层共用 `core/`，否则两份代码会越走越远，
最后变成「网页版和游戏版手感不一样」这种无解的 bug。
